# DNSLab 产品需求文档（PRD）

- **项目名称：** DNSLab
- **文档版本：** 0.1
- **产品版本目标：** v1.0 MVP
- **文档状态：** 待实现
- **项目类型：** 跨平台命令行网络诊断工具
- **目标语言：** C++23
- **目标平台：** Windows 10/11 x64、Linux x86_64（优先验证 Ubuntu 22.04+）

## 1. 产品概述

DNSLab 是一个面向开发者和网络学习者的 DNS 诊断 CLI。用户向 DNSLab 提供域名、记录类型和一个或多个 DNS 服务器后，工具会直接向指定服务器发送 DNS 查询，解析响应，并对比响应码、记录内容、TTL 与请求耗时，最终输出终端摘要和可保存的 JSON 报告；Markdown 报告列为后续小版本。

DNSLab 的核心不是“把 nslookup 的输出换一种格式”，而是把一次 DNS 排查过程变成**可对比、可复现、可导出的实验**：不同解析器是否都能响应？回答是否一致？是否存在超时或 SERVFAIL？CNAME 链是什么？每次查询耗时如何变化？

DNSLab 是诊断工具，不是递归解析器、DNS 服务器、抓包器或 DNSSEC 验证器。它不承诺仅凭一次查询就断定故障根因，而是提供证据、统计和谨慎的提示。

## 2. 问题与目标用户

### 2.1 要解决的问题

1. 用户通常需要手动分别运行多个命令，难以在同一轮实验中比较多个 DNS 服务器。
2. 常见命令能给出结果，但不方便批量采样、汇总延迟分布和导出报告。
3. DNS 失败可能发生在传输层，也可能是 DNS 响应码或回答内容的问题；用户容易把它们混为一谈。
4. CNAME、TTL、空答案、NXDOMAIN、SERVFAIL、超时等结果需要统一呈现，方便定位问题。

### 2.2 目标用户

- 正在学习 DNS、TCP/UDP 与网络协议的学生。
- 排查“部分网络能访问、部分网络不能访问”问题的开发者。
- 需要对多个指定 DNS 解析器进行可重复测试的技术支持人员。

### 2.3 主要使用场景

- 比较多个 DNS 服务器对同一个域名的回答是否一致。
- 查看 A、AAAA、CNAME、MX、NS、TXT 等记录及 TTL。
- 判断某个服务器是超时、无法建立 TCP 连接，还是返回 DNS 错误码。
- 连续查询多轮，观察延迟、成功率及回答变化。
- 把诊断结果保存成文件，附在 Issue、实验记录或技术报告中。

## 3. 产品目标与非目标

### 3.1 v1.0 目标

- 提供稳定、易懂、可脚本调用的跨平台 CLI。
- 能直接查询用户指定的 DNS 服务器，而不是无提示地依赖操作系统默认解析器。
- 支持多服务器对比、常见记录解析、延迟统计和结构化报告。
- 对畸形报文、超时、截断响应、服务器返回错误等情况有明确处理。
- 通过本地模拟 DNS 服务端建立可重复的自动化测试，不要求 CI 依赖公共 DNS。

### 3.2 v1.0 非目标

- 不实现完整递归解析、根服务器迭代查询或权威服务器发现。
- 不实现 DNSSEC 签名验证或证明某个答案可信。
- 不做全功能图形界面，不替代 Wireshark、dig 或系统网络管理工具。
- 不自动更改系统 DNS 设置、Hosts 文件、防火墙或路由。
- 不对公共 DNS 服务商作永久性排名，也不声称短时间测试能代表长期服务质量。
- 不在 v1.0 中实现 DoH（DNS over HTTPS）和 DoT（DNS over TLS）；列为后续版本能力。

## 4. 产品原则

1. **明确测试对象：** 报告必须显示实际查询的服务器地址、传输方式、记录类型与测试时间。
2. **区分错误层次：** 把网络超时、连接失败、报文无效和 DNS RCODE 分开呈现。
3. **不夸大诊断结论：** 提示应描述观察到的证据与可能原因，不把相关性写成确定根因。
4. **结果可复现：** 相同参数和本地测试服务器应能得到稳定、可自动检查的结果。
5. **隐私优先：** 不收集遥测，不把域名或查询结果发送到 DNSLab 自有服务。
6. **面向脚本：** 退出码、JSON 字段和报告格式应稳定，并有版本字段。

## 5. 范围与优先级

### 5.1 v1.0 必须实现（P0）

- Windows 与 Linux 的命令行构建和运行。
- 直接向 IPv4/IPv6 DNS 服务器发起查询。
- UDP 查询；如果响应设置了 TC（Truncated）位，则自动通过 TCP 重试同一 DNS 查询。
- 支持显式 TCP 查询模式。
- 支持 A、AAAA、CNAME、MX、NS、TXT、SOA 记录查询与基本解析。
- 解析 RCODE、Answer/Authority/Additional 中支持的记录、TTL、响应耗时。
- 同时查询多个 DNS 服务器并对比结果。
- 支持指定轮数并计算 min、median/p50、p95、max、成功率和超时次数。
- 终端表格输出；JSON 报告文件输出。
- 超时、参数验证、DNS 报文边界检查和明确退出码。
- 单元测试、基于本地假 DNS 服务器的集成测试、CI 与基本使用文档。

### 5.2 应尽量实现（P1）

- Markdown 报告。
- CNAME 链摘要和常见异常提示。
- IPv6 DNS 服务器地址与 DNS 查询目标域名的边界测试。
- 自定义超时、轮数、并发度和 EDNS UDP payload size。
- 可配置的慢响应阈值；默认不使用固定阈值给公共 DNS 排名。
- PTR 反向查询。

### 5.3 后续版本（不阻塞 v1.0）

- DoT 和 DoH，严格验证 TLS 证书，不允许默认跳过验证。
- 系统解析器结果对照模式，并明确它和直接查询的差异。
- IDN Unicode 域名输入及 IDNA 转换。
- DNSSEC 相关标志与记录展示（仅展示不等于验证）。
- 历史报告对比、批量域名清单、CSV 输出。
- 可选的 EDNS Client Subnet、Extended DNS Error（EDE）展示（若响应包含）。

## 6. 命令行接口需求

命令名为 `dnslab`。所有命令均支持 `--help`；程序支持 `--version`。

### 6.1 单服务器查询

```text
dnslab query example.com --type A --server 1.1.1.1
```

行为：查询指定域名及记录类型，展示 DNS 服务器、传输方式、耗时、RCODE、TTL 与答案。

### 6.2 多服务器对比

```text
dnslab compare example.com --type A \
  --server 1.1.1.1 \
  --server 8.8.8.8 \
  --rounds 10 \
  --timeout-ms 1500 \
  --output report.json
```

行为：每轮向每个服务器发送一次查询；同一轮的不同服务器请求可并发执行，但应受 `--concurrency` 上限控制。输出每个服务器的逐次结果和聚合统计。

### 6.3 指定 TCP 查询

```text
dnslab query example.com --type AAAA --server 1.1.1.1 --transport tcp
```

### 6.4 参数约定

- `query <name>`：执行一次查询。
- `compare <name>`：至少需要两个 `--server`；默认 10 轮。
- `--type`：接受 `A|AAAA|CNAME|MX|NS|TXT|SOA`，大小写不敏感；默认 `A`。
- `--server`：可重复指定；v1.0 要求使用 IPv4/IPv6 字面地址，可选端口；不得为了解析服务器名称而隐式调用系统 DNS。
- `--transport`：`auto|udp|tcp`；默认 `auto`。`auto` 先尝试 UDP，仅在收到 TC=1 的有效响应时通过 TCP 重试，不把所有 UDP 超时都静默改成 TCP。
- `--rounds`：1–100，默认 10；`query` 默认 1。
- `--timeout-ms`：每次请求的超时，默认 1500 ms；允许范围 100–30000 ms。
- `--concurrency`：并发请求上限，默认 8，最小 1，最大 64。
- `--output <path>`：写入报告；文件已存在时默认拒绝覆盖，需显式 `--force`。
- `--format table|json`：v1.0 默认 `table`；若指定输出路径且未给格式，按扩展名推断 JSON 格式；未知或当前版本不支持的格式应报错而非猜测。Markdown 格式列为后续小版本。
- `--edns-payload <bytes>`：P1；启用 EDNS(0) 时的 UDP payload 上限，默认值及实现需在技术设计中明确并测试。

服务器示例：

```text
--server 1.1.1.1
--server 1.1.1.1:5353
--server [2606:4700:4700::1111]:53
```

### 6.5 退出码

- `0`：所有请求均得到可解析的 DNS 响应；DNS 响应即使是 NXDOMAIN、REFUSED 或 SERVFAIL，也不单独导致此退出码变为非零。
- `1`：一个或多个请求发生传输失败、超时或无法解析的响应；报告仍尽可能写出。
- `2`：参数、域名、服务器地址或配置无效。
- `3`：报告输出失败或发生未能正常处理的内部错误。

程序不得仅因 DNS 返回 NXDOMAIN 就丢弃报告。自动化使用者应同时检查退出码与 JSON 中的 `rcode` / `transport_status` 字段。

## 7. 功能需求

### FR-001 参数与输入验证

- 验证域名长度、标签长度和可接受字符；v1.0 接受 ASCII 域名及已转成 Punycode 的名称。
- 自动容忍域名末尾的单个根点；内部查询名称应规范化为绝对域名语义。
- 对非法域名、非法 IP、无效端口、非法记录类型、范围外轮数与超时给出可操作的错误提示。
- v1.0 对原始 Unicode 域名应明确提示用户输入 Punycode，不得静默按本地代码页转换。

### FR-002 DNS 查询构造与关联

- 为每个请求生成事务 ID。
- 响应必须通过来源端点（UDP）、事务 ID、QR 标志和 Question 匹配等必要校验；不匹配的报文不得被当作当前请求成功结果。
- 对畸形报文、截断报文、错误长度、越界压缩指针和压缩指针循环进行安全处理，不得崩溃或越界读取。
- 查询响应中的名称比较遵循 DNS 名称不区分 ASCII 大小写的语义。

### FR-003 记录解析

- A：展示 IPv4 地址。
- AAAA：展示 IPv6 地址。
- CNAME：展示目标名称。
- MX：展示 preference 与 exchange。
- NS：展示目标名称。
- TXT：按 DNS TXT 字段结构解析；不能直接打印为可显示文本的数据应转义显示。
- SOA：展示 MNAME、RNAME、serial、refresh、retry、expire、minimum。
- 对尚不支持解码的资源记录，应至少安全地展示类型编号、TTL 和 RDATA 长度；是否显示原始十六进制需由实现设计决定。
- 保留记录所在 section 信息（Answer、Authority、Additional），避免将 Additional 中的附加记录误显示为直接答案。

### FR-004 响应状态

- 展示常见 RCODE：NOERROR、FORMERR、SERVFAIL、NXDOMAIN、NOTIMP、REFUSED；其他值显示数字代码及 `UNKNOWN`。
- 将协议响应与传输状态分开记录，例如 `rcode=SERVFAIL` 与 `transport_status=ok` 可以同时成立。
- NOERROR 但查询类型没有直接答案时，显示“NOERROR / 无直接答案”，不要未经证据直接宣告域名不存在。
- 若存在 CNAME，应显示 CNAME 记录以及本次响应中实际包含的后续记录；不承诺 v1.0 自动递归追踪所有 CNAME 跳转。

### FR-005 UDP/TCP 行为

- 默认通过 UDP 发送 DNS 查询。
- 如果收到有效响应且 TC 位被设置，使用 DNS over TCP 重试同一查询；TCP 消息必须按两字节长度前缀读取完整 DNS 消息。
- TCP 连接、发送、读取和关闭均有超时及错误处理。
- UDP 超时不应被误报为 NXDOMAIN 或其他 RCODE。
- 网络接口错误、连接拒绝、超时、无效响应均有独立且机器可读的状态。

### FR-006 多服务器对比

- 每个服务器独立记录逐轮结果；一个服务器失败不能中止其他服务器测试。
- 每一轮尽可能在接近的时间窗口内对多个服务器并发发起请求，并记录每次请求开始时间和耗时。
- 汇总每台服务器的成功数、失败数、超时数、成功率、min、median/p50、p95、max。
- 统计指标仅基于成功且可解析的响应耗时；必须同时报告样本数。
- p95 的计算方法在文档与测试中固定；样本量较小时应提醒结果仅供参考。
- 不根据单次延迟或单一轮结果自动宣布某个 DNS 服务商“最快”或“最好”。

### FR-007 结果差异与诊断提示

- 对比不同服务器返回的 RCODE 和规范化后的 Answer 摘要。
- 提示可能的观察结果：某台服务器独立超时、所有服务器超时、服务器返回不同答案、某台服务器返回 SERVFAIL/REFUSED、查询得到 NXDOMAIN、UDP 响应被截断后 TCP 回退成功或失败。
- 每条提示应包含证据，并使用“可能原因”措辞；例如不同答案可能与缓存、地理调度、策略或 DNS 更新传播有关，不得直接判定其中某一方错误。
- TTL 不同本身不是错误，也不能单独证明解析器缓存异常。
- v1.0 不将网络时延与 DNS 服务商质量作无上下文的跨地区比较。

### FR-008 输出与报告

- 终端表格适合人工查看；JSON 用于自动化和后续分析；Markdown 为 P1。
- JSON 顶层至少包含：`schema_version`、`tool_version`、`started_at`、`duration_ms`、`query`、`options`、`results`、`summary`、`warnings`。
- 每个结果至少包含：服务器地址、传输方式、开始时间、耗时、传输状态、RCODE、flags、问题记录、解析出的资源记录、错误信息。
- 聚合统计应明确区分请求总数、成功响应数、传输失败数与 DNS 非 NOERROR 数。
- 时间使用带时区的 RFC 3339 格式；延迟使用毫秒数值；枚举使用稳定字符串。
- 写报告失败时给出非零退出码；若标准输出仍可用，应把简洁错误写到 stderr。
- JSON Schema 需要随代码发布，并通过测试验证关键字段与类型。

### FR-009 隐私与安全

- 不包含遥测或自动上传功能。
- 文档明确提示：查询域名会发送给用户指定的 DNS 服务器，服务器可能记录查询；TXT 等记录内容可能包含验证令牌等数据。
- 不在默认日志中记录与诊断无关的环境变量、系统凭据或完整用户环境信息。
- 解析不可信网络数据时必须做长度校验、范围校验与资源上限控制。
- 不提供“忽略证书验证”选项作为后续 DoH/DoT 的默认或推荐模式；安全传输功能必须验证证书和主机身份。

## 8. 非功能需求

### NFR-001 可移植性

- 使用 C++23 和 CMake。
- 核心 DNS 报文解析逻辑尽量与平台网络 I/O 分离。
- 至少在 Windows x64 和 Linux x86_64 通过 CI 编译与测试。

### NFR-002 稳定性

- 无效输入或恶意构造的 DNS 响应不得导致未处理异常、崩溃、越界访问或无限循环。
- 所有 socket 操作均受超时和取消路径控制。
- 多服务器查询应能处理单个服务器永久无响应的情况，并最终结束。

### NFR-003 可维护性

- 协议解析、传输层、统计计算、终端输出、报告序列化和 CLI 参数解析应分层实现。
- 关键协议字段与错误状态使用明确类型，不以散落的魔法数字表示。
- 对公共 API、JSON schema 和退出码提供文档。

### NFR-004 性能

- 对常见域名与常见记录类型，单个解析和输出不得引入显著于网络等待的额外延迟。
- 并发数、轮数和报告大小必须有上限。
- v1.0 不以极限吞吐为目标；优先保证结果正确、超时可控与报告准确。

### NFR-005 可测试性

- 协议解析器支持直接使用内存字节数组进行单元测试。
- 集成测试应运行本地模拟 DNS 服务器，覆盖成功、NXDOMAIN、SERVFAIL、无响应、TC 截断、畸形包、错误事务 ID 与 TCP 回退。
- 默认 CI 不依赖 Google、Cloudflare 或其他公共 DNS 的可用性。
- 可选外网冒烟测试不得成为合并代码的唯一验证手段。

## 9. 建议模块边界

以下为实现建议，不要求目录名完全一致：

- `cli`：命令与选项解析、参数校验、退出码映射。
- `dns::wire`：DNS 报文编码/解码、压缩名称解析、资源记录解码。
- `dns::transport`：UDP、TCP、超时与取消。
- `query`：单次查询和多服务器调度。
- `stats`：延迟统计、成功率与回答差异比较。
- `diagnostics`：基于已观测证据生成提示。
- `output`：终端表格、JSON 和 Markdown 输出。
- `tests`：报文单元测试、本地模拟 DNS 服务器与 CLI 集成测试。

可以选用跨平台网络库以避免大量平台专用 socket 代码，但应在设计文档中写明依赖、许可证和构建方式。不要在第一版为了未来 DoH/DoT 提前搭建复杂插件系统。

## 10. 验收标准

v1.0 发布前必须全部通过：

1. Windows 和 Linux 均可通过记录在 README 中的命令完成配置、构建和测试。
2. `dnslab --help`、`dnslab --version` 正常工作；缺少必要参数时给出示例并返回退出码 2。
3. 对本地模拟服务端查询 A、AAAA、CNAME、MX、NS、TXT、SOA，输出的解析结果与测试夹具一致。
4. 收到 NXDOMAIN、SERVFAIL、REFUSED 时显示准确 RCODE，不把它们误报为网络超时。
5. 模拟服务器不响应时，在指定超时范围内结束并记录 timeout；其他服务器的结果仍会保留。
6. UDP 响应带 TC 位时，`auto` 模式可通过 TCP 获取完整响应；显式 TCP 模式能够正确读取分段到达的数据。
7. 错误事务 ID、错误来源、截断报文、越界压缩指针、压缩指针循环等测试不会污染结果或导致崩溃。
8. 多服务器测试输出逐次结果和统计指标；统计脚本对固定样本得出预期的 min、median、p95、max 和成功率。
9. JSON 报告通过 JSON Schema 校验，包含 schema/tool 版本及所有必要状态字段。
10. 已存在的报告文件默认不会被覆盖；使用 `--force` 时才覆盖。
11. 由于外部网络不可用而失败的公共 DNS 测试不得使离线 CI 失败；CI 中的核心集成测试必须使用本地模拟服务端。
12. README 包含安装/构建、示例、退出码、报告样例、支持范围、已知限制和隐私说明。

## 11. 里程碑建议

### M0：CLI 与协议设计

确定命令行参数、错误模型、JSON schema、DNS 报文编码/解码接口；建立 CMake、格式化与静态检查配置。

### M1：基础 DNS 查询

完成 UDP 查询、A/AAAA 记录、常见 RCODE、超时、服务器与响应关联验证；建立本地模拟 DNS 测试。

### M2：完整性与传输可靠性

完成压缩名称解析安全检查、更多资源记录、TCP 查询与 TC 自动回退、畸形报文测试。

### M3：多服务器对比

实现多服务器并发调度、轮数控制、统计指标、答案差异摘要与终端表格。

### M4：报告、文档与发布

实现版本化 JSON 报告、退出码、覆盖保护、Windows/Linux CI、README 和 v1.0 发布检查。

### v1.1 候选

按 v1.0 使用反馈再决定优先级：Markdown 报告、IDN 输入、PTR、DoT、DoH、系统解析器对照、历史结果比较。

## 12. 主要风险与应对

| 风险 | 影响 | 应对策略 |
|---|---|---|
| DNS 名称压缩指针解析存在边界错误 | 崩溃或安全问题 | 单独实现解析器；限制跳转次数；覆盖循环、越界和截断测试 |
| 把 DNS 错误码与网络错误混淆 | 诊断误导 | 在数据模型、JSON 和 CLI 中分别存储 transport status 与 RCODE |
| 过度解释不同 DNS 答案 | 错误地判定某服务器故障 | 输出观测事实与可能原因；不将答案不同直接判错 |
| 统计轮数少导致 p95 不稳定 | 产生虚假的性能结论 | 报告样本数和方法；提醒小样本不稳定；不做全球排名 |
| CI 依赖公网 DNS | 构建随机失败 | 使用本地模拟 DNS server 测试协议与错误路径 |
| 过早加入 DoH/DoT | 延迟 MVP，增加 TLS/HTTP 复杂度 | v1.0 只保证 UDP/TCP；加密传输留到后续版本 |
